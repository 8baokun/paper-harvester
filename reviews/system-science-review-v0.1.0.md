## 一、系统形式化（模型1：系统形式化）

### 1.1 边界划定

**系统边界**：paper-harvester 是一个**文献检索与下载的自动化工具系统**，边界如下：

| 在系统内 | 在系统外 |
|----------|----------|
| 8个 Python 脚本（检索+下载+引文） | 用户（发出检索意图的人） |
| SKILL.md（Agent 调度逻辑） | NCPSSD/微信/OpenAlex 等外部平台（系统环境） |
| references/（路由策略与源说明） | 操作系统与 Python 运行时（基础设施） |
| 输出产物（PDF/MD/JSON/BibTeX） | WorkBuddy Agent 框架（宿主环境） |

**边界判定**：边界划在"脚本+配置+输出"层面是合理的。但当前边界存在一个**模糊地带**——SKILL.md 既是系统组分（Agent 读它来调度脚本），又是系统接口（用户通过 Agent 间接读它来理解能力）。这种"自指"不是缺陷，而是 Agent Skill 系统的固有特征。

### 1.2 组分识别

| 功能分系统 | 脚本 | 功能 |
|------------|------|------|
| 英文检索分系统 | search_openalex.py, search_semantic_scholar.py, search_crossref.py, search_arxiv.py | 多源元数据检索 |
| 中文检索分系统 | search_ncpssd.py | NCPSSD 检索+登录+下载 |
| 微信下载分系统 | download_wechat.py | 公众号文章提取+转换 |
| OA 下载分系统 | download_oa.py | OA PDF 下载+校验 |
| 引文生成分系统 | build_bib.py | BibTeX 生成 |
| 调度控制分系统 | SKILL.md | Agent 执行流程编排 |

### 1.3 结构映射

当前结构是**星型调度结构**——SKILL.md 为中心，6个功能分系统为辐射节点：

```
                    [SKILL.md 调度中心]
                   /    |    |    |    |    \
            英文检索  中文检索  微信下载  OA下载  引文生成
              (4脚本)  (1脚本)  (1脚本)  (1脚本) (1脚本)
```

**结构特征**：功能分系统之间**无直接耦合**——英文检索不调用中文检索，OA 下载不调用引文生成。所有跨分系统的数据流必须经过 SKILL.md（即 Agent）中转。这是 Agent Skill 的标准结构，但意味着系统整体功能 = Agent 的调度能力 × 各分系统功能之和。

### 1.4 功能定位

系统对外输出的整体功能：**从"用户研究意图"到"本地文献库+BibTeX"的自动化转换**。

### 1.5 环境标注

| 环境要素 | 与系统的交换方式 |
|----------|-----------------|
| NCPSSD 平台 | 系统从平台获取题录+PDF（信息流入） |
| 微信公众号平台 | 系统从平台获取文章HTML（信息流入） |
| OpenAlex/Crossref/S2/arXiv API | 系统从API获取元数据（信息流入） |
| 本地文件系统 | 系统向磁盘写入PDF/MD/JSON/BibTeX（信息流出） |
| WorkBuddy Agent | Agent向系统传入检索意图+参数（控制信号流入），系统向Agent返回结果（反馈信号流出） |

### 1.6 系统复杂度判定

paper-harvester 是一个**中等复杂度的开放系统**——不是简单系统（多源异构、需适配各平台API变化），但也不是复杂巨系统（组分数量有限、耦合关系清晰、无涌现性）。**系统科学方法的价值在此适中**——结构化分析有益，但不宜过度工程化。

## 二、信息变换与共轭控制链分析（模型2）

### 2.1 链路追踪

从"用户研究意图"到"本地文献库"的信息变换链路：

```
用户意图("帮我查业法财融合的文献")
  ↓ [Agent 意图解析变换]
检索式("业法财融合" → IKTE="业法财融合" OR ...)
  ↓ [API 调用变换]
平台响应(JSON rows)
  ↓ [解析变换 _parse_article()]
统一文献格式(title/authors/year/doi/oa/pdf/...)
  ↓ [路由判断变换]
下载路径决策(NCPSSD→login+download / OA→download_oa / 微信→download_wechat / 🔒→locked)
  ↓ [执行变换]
本地文件(PDF/MD/JSON)
  ↓ [引文变换]
BibTeX(lit.bib)
```

### 2.2 变换分析——语义漂移风险

| 变换环节 | 输入 | 输出 | 语义漂移风险 |
|----------|------|------|-------------|
| Agent意图解析 | 自然语言 | 检索式 | 🟡 中——用户说"法学"可能指学科、期刊或关键词 |
| API调用 | 检索式 | JSON rows | 🟢 低——API格式固定 |
| _parse_article() | JSON row | 统一dict | 🟡 中——字段映射可能遗漏（如 NCPSSD 的 `type` 字段未充分利用） |
| 路由判断 | 统一dict | 下载/跳过 | 🔴 高——`oa:True` 硬编码（见2.4） |
| 下载执行 | URL | 本地文件 | 🟡 中——HTML 解析可能失败 |
| BibTeX生成 | dict | .bib | 🟢 低——格式映射直接 |

### 2.3 放大/衰减评估

- **放大机制**：NCPSSD 一个关键词检索返回 36513 条结果——**检索放大**（1个意图→数万条候选）
- **衰减机制①**：pageSize 限制为 `min(limit, 50)`——API 层面的结果截断
- **衰减机制②**：下载流程中 HTML 解析 → 候选URL构造 → 逐个尝试，每一步都可能失败——**下载链路衰减**
- **衰减机制③**：OA 下载只看 `oa:True` + `pdf` 字段，不检查 URL 可达性——**路由层假阳性**（标记为可下载但实际不可达）

### 2.4 关键缺陷诊断——"维纳悖论"式控制盲区

**问题**：`search_ncpssd.py` 第159行硬编码 `"oa": True`——所有 NCPSSD 检索结果都被标记为"OA可下载"。但实际上，NCPSSD 下载需要登录，未登录时下载链路断裂。

**系统科学诊断**：这是控制链路的**信息映射失真**——规范空间（"NCPSSD注册后免费下载"）被错误映射为操作空间（"oa=True可直接下载"）。控制信号在"检索→下载"的共轭变换中发生了语义漂移：`oa` 字段本意是"开放获取"（无需认证即可获取全文），但 NCPSSD 的"免费"不等于"开放"——它需要注册认证。

**纠正建议**：将 NCPSSD 结果的 `oa` 字段改为 `"oa": "ncpssd_login"`（条件性OA），与真正的 OA（`"oa": True`）区分。路由判断时，`ncpssd_login` 类型需要先执行 login 变换，再执行 download 变换。

### 2.5 社会控制三条件检验

| 条件 | 满足情况 |
|------|----------|
| 规范行为空间（界定合法/非法操作） | ✅ oa-routing.md 明确三层路由 + 禁止项 |
| 目标差信息（现实与目标的偏差） | ⚠️ 部分满足——下载失败有 note 但无系统级重试 |
| 控制能力（将越界行为回拉） | ❌ 下载失败后无降级策略（不尝试其他源） |

## 三、行为可能性空间与规范调控（模型3）

### 3.1 当前可能性空间描绘

系统在"文献获取"这一行为空间中的调控模式：

| 调控模式 | 当前实现 | 空间操作 |
|----------|----------|----------|
| 选择（可以） | 用户可选关键词/数量/是否下载 | ✅ 空间保留 |
| 必须（应当） | 下载间隔≥2秒、PDF校验前5字节 | ✅ 空间特定收缩 |
| 不得（禁止） | 不绕过付费墙、不爆破登录、不用Sci-Hub | ✅ 空间特定排除 |

**评价**：三种调控模式都有覆盖，合规设计扎实。

### 3.2 空间弹性问题

**问题**：当前系统的行为可能性空间是**刚性的**——下载失败=流程结束，没有"弹性回退"。

具体表现：
- NCPSSD 下载失败 → 直接标记 error，不尝试其他源
- OA 下载 URL 404 → 标记 not-pdf，不尝试 Unpaywall 备选
- 微信文章需要 JS 渲染 → 直接返回"无法提取"，不尝试 headless browser

**系统科学诊断**：规范空间（设计意图）与实际行为空间（执行结果）之间存在**目标差**——设计者期望"下载成功率高"，但实际系统在链路任一环节断裂时就放弃。缺少负反馈回路——没有"检测到失败→调整策略→重试"的闭环。

### 3.3 感知偏差模型

脚本对平台的"感知"依赖 HTML 解析和 API 调用。当平台改版时（NCPSSD 改版、微信反爬升级），脚本的"感知"会偏离现实——**感知偏差导致行为偏差**。当前系统没有"感知校验"机制——不检查返回的 HTML 是否是预期的页面结构。

## 四、多体功能耦合分析（模型5）

### 4.1 功能分系统耦合关系

当前各分系统之间的耦合关系：

| 分系统A → 分系统B | 耦合类型 | 耦合强度 |
|-------------------|----------|----------|
| 英文检索 → OA下载 | 数据耦合（JSON管道） | 中（需Agent中转） |
| 中文检索 → NCPSSD下载 | 功能耦合（同一脚本内） | 强（一体化设计） |
| 任意检索 → BibTeX生成 | 数据耦合（JSON管道） | 弱（单向，无反馈） |
| 英文检索 ↔ 中文检索 | 无耦合 | 无 |
| OA下载 ↔ NCPSSD下载 | 无耦合 | 无 |

### 4.2 序参量识别

系统的**序参量**（支配各子系统协同行为的参量）是什么？

当前系统的序参量是**统一的文献数据格式**——所有检索脚本输出 `{"title", "authors", "year", "source", "doi", "oa", "pdf", "url"}` 格式的 JSON。这个格式规范支配了检索、下载、引文三个子系统的协同。

**问题**：统一格式是隐含的（各脚本各自实现，无 schema 约束），而非显式的（无 dataclass/pydantic 模型）。当某个脚本输出格式偏离时，下游脚本会静默失败——**序参量的支配力缺乏强制保障**。

### 4.3 同构异功/同功异构辨识

| 现象 | 表现 |
|------|------|
| 同构异功 | search_ncpssd.py 和 search_openalex.py 结构相似（输入关键词→输出JSON列表），但功能不同（一个走表单API、一个走REST API） |
| 同功异构 | NCPSSD下载和OA下载都"把PDF存到本地"，但实现路径完全不同（一个需登录+HTML解析、一个直接urllib下载） |

**启示**：当前各脚本的"同功异构"是合理的——不同平台需要不同的下载策略。但缺少一个**抽象层**来统一"下载"这个功能，导致 Agent 调度时需要区分不同脚本。

### 4.4 混沌边缘

系统当前处于**强管制区**——每条路径都是预设的，没有自适应空间。改进方向是向"混沌边缘"移动：保留合规底线（不绕付费墙），但在失败时允许自适应尝试（如换源、重试、降级）。

## 五、自组织与他组织双模控制（模型9）

### 5.1 当前模式辨析

| 维度 | paper-harvester 表现 |
|------|---------------------|
| 控制中心 | SKILL.md（他组织——Agent 按 SKILL.md 编排） |
| 规则生成 | 全部自上而下（用户无自定义空间） |
| 信息流向 | SKILL.md→脚本（指令传递），无反向反馈 |
| 演化方式 | 间断性（开发者手动更新脚本） |

**诊断**：当前系统是**纯他组织模式**——所有逻辑预设、所有路径固定。缺少自组织能力——系统不能根据运行经验自我调整。

### 5.2 "虚拟存在"的规则

系统中的"规则"（如下载间隔2秒、pageSize上限50、PDF校验前5字节）都是**显式存在**的（硬编码在脚本中），而非"虚拟存在"的（在实践中涌现）。这意味着规则调整需要修改代码——调整成本高、响应速度慢。

### 5.3 双模耦合建议

引入自组织元素：
- **配置化**（他组织→半自组织）：将硬编码参数提取到 config.py，用户可根据经验调整
- **反馈积累**（自组织核心）：记录下载成功率、各源响应时间，形成运行日志，指导参数优化
- **区别技术**：系统根据下载失败的具体模式（404/403/超时/非PDF），自动区别处理而非统一标记error

## 六、综合集成方法论（模型6）

### 6.1 人-机-网结合评估

| 维度 | 当前状态 | 差距 |
|------|----------|------|
| 人（专家智慧） | Agent 理解用户意图、选择检索策略 | ✅ 充分 |
| 机（计算能力） | 脚本执行检索/下载/转换 | ✅ 充分 |
| 网（信息集成） | 多源检索（NCPSSD+OpenAlex+Crossref+S2+arXiv+微信） | ✅ 充分 |
| 从定性到定量 | 检索结果排序权重（相关性0.35/被引0.25/...） | ⚠️ 权重定义在SKILL.md中但脚本未实现 |
| 研讨厅模式 | 无——用户与系统无交互式反馈 | ❌ 缺失 |

### 6.2 关键差距

**排序权重未实现**：SKILL.md 第47行定义了排序权重（相关性0.35/被引0.25/时效0.20/来源0.10/OA0.10），但没有任何脚本实现了这个排序逻辑。检索结果只是按API返回顺序截断。这是**设计意图（规范空间）与实现状态（实际空间）之间的目标差**。

## 七、复杂性、偶然性与不确定性三分法（模型8）

### 7.1 三分法诊断

| 来源 | 表现 | 当前应对 |
|------|------|----------|
| **复杂性**（系统内部结构） | 多平台API格式不同、HTML结构各异 | 每个平台独立脚本，格式各异 |
| **偶然性**（外部随机扰动） | 网络超时、平台临时不可用、微信链接失效 | 基础 try-except，无重试 |
| **不确定性**（涌现的不可预测） | 平台改版导致解析失效、NCPSSD下载流程变化 | 无——发现后需人工修复 |

### 7.2 减少不确定性的途径评估

| 途径 | 当前实现 | 改进方向 |
|------|----------|----------|
| 建模仿真减少复杂性 | 各平台独立解析模型 | 统一数据schema + 平台适配器模式 |
| 反馈机制校正偶然性 | 无重试、无降级 | 指数退避重试 + 多源降级链 |
| 综合集成汇聚知识 | 多源检索并列 | 检索结果跨源去重 + 置信度评分 |
| 滤波机制过滤波动 | 无 | 下载结果校验（已有PDF前缀校验，需扩展到内容校验） |
| 序参量识别趋势 | 无 | 运行日志分析各源成功率趋势 |

### 8.2 改进方案的系统科学分类

**稳态转换类**（改变系统整体功能）：
- 方案1（微信批量导出）：从"单篇"到"批量"是功能跃迁
- 方案2（ISSN检索）：从"关键词"到"关键词+ISSN"是检索维度扩展
- 方案3（多源降级）：从"单链路"到"降级链"是控制结构改变

**负反馈补全类**（修复控制链断裂）：
- 方案3（多源降级）：核心是建立"失败→换源→重试"的负反馈回路
- 方案6（配置化）：让参数可调是反馈调节的前提

**综合集成类**（增强信息汇聚）：
- 方案5（sidecar元数据）：关系集成——每篇文献的来源/时间/DOI追溯链
- 方案7（Excel I/O）：批量信息集成接口

**接口适配类**（降低耦合摩擦）：
- 方案4（分享文本提取）：用户接口适配
- 方案8-10：输出/分发适配

### 8.3 改进方案的耦合关系

```
方案6(配置化) ──→ 方案3(多源降级) ──→ 方案5(sidecar元数据)
      │                                      │
      ↓                                      ↓
方案2(ISSN检索)                        方案7(Excel I/O)
                                          
方案1(微信批量导出) ──→ 独立模块，与上述无强耦合
```

**实施顺序建议**：先做方案6（配置化基础设施），再做方案3（多源降级），然后方案2和方案1并行，最后方案5和方案7。

## 九、当前系统的"目标差"诊断（模型7）

### 9.1 目标差八条成因对照

| # | 成因 | paper-harvester 表现 | 严重度 |
|---|------|---------------------|--------|

### 9.2 稳态判定

系统当前处于**初始稳态**（v0.1.0 刚建立）。核心功能（检索+下载）已验证可用，但尚未经历"远离平衡"的挑战（平台改版、大规模使用、边缘场景）。

**发展判断**：当前不是"发展"（稳态转换），而是"完善"（同一稳态内的组分优化）。真正的稳态转换将在以下任一条件触发时发生：
- 用户实际使用中暴露系统性问题（如 NCPSSD 下载链路不通）
- 改进方案1/2/3中任一实现后，系统功能发生跃迁
- 外部环境变化（如 NCPSSD 开放API、微信关闭公开访问）
